# Typed operations: matched incremental adaptation rejected

Decision: **reject the typed-format candidate and retain round-nine step 200 with
the existing v1 app format**. The range arm is a control and is not promoted.
No application, production metadata, or ADR changed. The compiler and all v2
inference are isolated Python development code.

## What was tested

[FORMAT.md](FORMAT.md) defines terminal-punctuation and single-token-deletion
operations that compile to ordinary v1 span edits. Other edits keep their existing
range representation. The compiler never repairs or drops invalid operations and
always applies the existing validator mirror after compilation.

Both trained arms started from the retained round-eight step-200 adapter on the
same pinned Qwen base, using the same 100 examples in the same source order,
100 steps, seed 20260824, batch size 1, learning rate 1e-5, rank 8, scale 20, and
last 16 layers. Only system/target representation and data/output paths differed.
The data contains the previous balanced 80 rows plus 20 new paired-context rows.
The final checkpoint alone was evaluated, with no prompt or budget revisions.

This is an incremental feasibility comparison. The starting adapter was already
trained for v1, so it is not an unbiased from-scratch architecture comparison.
Matched examples/steps do not mean equal token or compute budgets: v2 has a longer
system instruction and shorter outputs. The 640-token limit truncated neither
arm; full-template maxima were 407/408 for range train/validation and 468/469 for
typed. The measured training peaks were 15.049 GB and 17.417 GB respectively.

## Frozen results

The Python MLX comparison used 91 cases: 55 existing validation cases, the prior
24 diagnostic cases, and 12 new paired-context validation cases. These are
experimental checks, not representative release qualification.

| Exact output | Retained baseline | Matched range | Typed |
| --- | ---: | ---: | ---: |
| Existing validation /55 | 42 | 44 | 13 |
| New context /12 | 6 | 12 | 6 |
| Diagnostic statements /6 | 6 | 5 | 3 |
| Diagnostic filler /4 | 0 | 2 | 2 |
| Diagnostic repetition /4 | 2 | 3 | 0 |
| Diagnostic mid-sentence /5 | 0 | 5 | 5 |
| Diagnostic new-sentence /5 | 5 | 0 | 0 |
| **Total /91** | **61** | **71** | **29** |

Typed loses 47 outputs that the retained model gets right, and 50 that the range
control gets right. It fails the predeclared retention and total-quality gates.
The range control itself loses 14 previously correct retained-model outputs,
including all five diagnostic new-sentence cases, despite its higher total.

Typed generated 91 valid compiled plans: 72 end-only plans, 16 filler-deletion
plans followed by an end operation, and three empty plans. It emitted 88 end and
16 delete operations, **zero range edits**, and no repetition deletions. Training
contained 74 capitalization range edits and 16 vocabulary range edits, but neither
behavior appeared in typed inference. All 16 emitted deletions target literal
`um` or `uh`; their source tokens and resulting outputs are recorded in
`output-analysis.json`. Structural acceptance did not establish cleanup quality.

The new format removed arithmetic from the emitted operations, but the model
collapsed toward a small subset of valid outputs. It did not learn the complete
hybrid operation set within this budget. Token loss (typed validation 0.705 to
0.057; range 0.033 to 0.023) did not reveal that sequence-level failure. Mean output
length fell from about 44 tokens to 22, which is not useful while quality fails.
These numbers do not establish a latency improvement.

`comparison.json`, `decision.json`, `changed-outputs.json` and `output-analysis.json`
preserve counts, individual regressions, raw generated bytes, compiled plans and
operation coverage. No post-selection historical/adversarial inference or native
v2 integration was run because typed failed the eligibility gate.

## Verification

- All 317 canonical targets round-trip exactly through the typed compiler and
  reproduce their expected text through the validator mirror.
- All 167 matched train/loss-validation targets also round-trip and validate.
- Thirty Python tests pass, including unknown/extra keys, boolean and out-of-range
  indices, duplicate JSON keys, trailing data, protected URLs, substantive-word
  deletion, reserved corrections, ordering and duplicate-end rejection.
- The comparison scorer's positive, regression, no-improvement and incomplete-file
  controls pass. Both shell scripts pass syntax checks.
- Both training jobs, both affine 4-bit/group-64 exports and all three 91-case
  evaluations completed with exit 0. Input hashes and starting adapter stayed
  unchanged. Resolved configurations differ only in data/output paths.
- Export tokenizer, template and license hashes exactly match the base.
- Retained-baseline outputs/outcomes on the shared 55 cases match the prior native
  Swift run exactly. This checks that baseline subset; it does not prove native
  equivalence for the new compiler or every evaluation input.

## Reproduction and limits

Run `python3 Training/test_typed_operations.py` and this directory's
`test_score.py` for structural/selection checks. `prepare.py` requires a fresh
`.context/cleanup-typed` directory; `train.sh` then runs the two arms sequentially.
`export_evaluate.sh` exports both arms and evaluates all three models. Existing
prediction files are never overwritten; use new paths for reproduction.

`input-hashes.json` freezes inputs/compiler/starting adapter. `execution-hashes.json`
records the execution/scoring scripts. Artifact manifests record exported weights
and adapter hashes. Large rejected weights remain local under
`.context/cleanup-typed/{range,typed}` and are not committed to Git.

The paired-context data uses fixed context phrases, so its generalization is
limited: the range control learns the new 12-case contexts but fails the older
new-sentence context phrasing. Do not treat that as solved context conditioning.

This run does not justify another repeat of the same 100-step hybrid-format
continuation. The specific next design question is whether a uniform operation
schema (instead of mixing `o` operations with `s/e` edits) and broader paired
context coverage can avoid the observed missing-operation behavior. That would
need a separately frozen protocol and data budget, preferably trained for the
complete schema rather than relying on a small migration from v1 weights. The
current result neither proves that alternative works nor justifies a production
schema change, more GPU rental, or relaxing the quality gates.
